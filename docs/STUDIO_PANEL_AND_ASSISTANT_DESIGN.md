## 一、背景与核心定位

本插件服务的目标用户主要是**“不懂复杂生图术语、希望零门槛快速出图并挑图”**的创作者。工作台左栏虽然提供了「参数表单」和「创作助手」两种形态，但目前偏向“功能逐批往上堆”，导致高频场景变重、参数与模型真实能力脱节。

基于这一核心定位，两个模式的**理想分工**应当是前后接力的流水线：

1. **创作助手（ChatPanel）—— 负责「从 0 到 1」**
   - 依托大模型（Agent）的世界知识与温和的澄清引导，把用户模糊的中文想法一步步打磨成契合当前（或更合适）模型的专业英文提示词，并支持自然语言多轮修改。
   - 目标是让不懂摄影、构图或模型偏好的新手**“说话就能出好图，上手零压力”**。
2. **参数表单（Rail）—— 负责「从 1 到 N」**
   - 面向**「快速换词 + 调画幅比例 + 多张抽卡（1~4 张）」**以及**垫图重绘**的高频操作。
   - 当用户从助手拿到满意的提示词、或从画廊「带回参数」后，能在极紧凑的视野内直接改词、切比例、开多张连抽。

## 二、当前设计诊断（代码与交互现状）

以下是通过代码走查发现的主要偏差，供评估与取舍：

### 2.1 创作参数面板（`src/studio/Rail.jsx` 等）

1. **控件状态与后端真实能力不一致（容易误导用户）**
   - **默认 `CFG = 0` 时「排除项」静默失效**：`sdxl-lightning`、`hyper-sdxl-8step`、`sdxl-turbo` 的默认 `cfg` 均为 `0`，而 `remote/daemon.py` 仅在 `cfg > 0` 且管线支持时才传递 `negative_prompt`。当前切换模型时仍会把 `negativeHint` 填入表单，选择风格也会追加负向词，界面上却未做有效区分，导致用户填写了实际会被后端忽略的参数。
   - **图生图模式下「画面设置」继续可调但实际无效**：`remote/daemon.py` 在存在参考图走 img2img 分支时，出图尺寸跟随参考图、不再传 `width / height`。但表单下方「画幅比例 / 1:1 推荐尺寸 / 自定义宽高」依然可点且高亮，标题栏也继续显示旧宽高，容易产生误解。
2. **「风格预设」与模型定位重叠且黑盒拼接**
   - 5 个「风格预设」（`src/studio/presets.js`）本质上是静态的英文后缀 + 负向词拼接，在提交时暗箱拼入，提示词框不可见；且将“视觉媒介”（摄影/原画/水墨/3D）与“题材”（赛博朋克）混为一谈，容易和顶栏 9 个专精模型（如 `RealVisXL`、`Animagine`）语义打架，或与大模型生成出来的风格词重复叠词。
3. **「画面设置」三层平铺、空间预算超载**
   - 同一个 `width × height` 状态在左栏同时占用了「画幅比例」「1:1 推荐尺寸」「自定义宽高」和两行解释文案 `sizeHint`。点 `1:1 推荐尺寸` 会把当前比例强行打回 `1:1`，而 `16:9` 等比例缺少档位选择。
   - 上方常驻「灵感示例」、展开后的 4 维「润色建议」和 5 个风格方块把 320px 宽面板的首屏高度撑爆，反而把最高频的**「生成张数（1~4）」**埋进了最底部默认折叠的「高级设置」里。
4. **细节与对称性缺失**
   - `ChatPanel` 有「沿用上张构图（锁定种子）」开关，而 `Rail` 只有裸数字框，回填种子后恢复随机只能手动删空。
   - `src/dict/zh.js` 的 `studio.prompt.englishHint` 文案仍引导用户“去创作助手里转成英文”，但输入框右下角其实已提供 `转为英文` 按钮。
   - 大量功能标签与提示停留在 `10.5px`（`src/styles/panel.css`），可读性偏弱。

### 2.2 AI 助手设计与代码组织（`lib/intent.js`、`lib/enhance.js`、`lib/llm.js`、`src/studio/hooks/useChatThread.js` 等）

1. **「模型知识」未沉淀为统一来源，散落在各处**
   - `models/*.json` 已经沉淀了非常完整的模型画像（`family`、`description`、`promptStyle`、`qualityPrefix`、`steps`、`cfg`、`negativeHint`、`supportsImg2Img`、`steadySeconds`、`gpus`）。
   - 但 `lib/intent.js` 只读取了当前模型的一小部分（`promptStyle`、`qualityPrefix`），并不知道其它 8 个模型的存在与专长，也无法判断当前模型是否吃负向词；`lib/enhance.js` 甚至还在手写过时的 `FAST_PRESETS = ['sdxl-lightning', 'sdxl-turbo']`（遗漏了 `hyper-sdxl-8step` 与 `flux2-klein-4b`），没有复用模型的 `promptStyle`；`lib/tools.js` 注册给 DSH 对话 Agent 的工具也只暴露了 ID 枚举，缺少模型用法与最佳实践说明。
2. **LLM 调用层（`lib/llm.js`）为单轮纯文本结构**
   - `invokeLlm` 目前只接收单个 `prompt` 字符串并包装成单条纯文本 `user` 消息，没有多轮对话历史通道，也还没有预留多模态（图像内容块）入参，限制了后续“多轮自然澄清”与“参考图理解”的演进空间。
3. **澄清机制（`clarify`）过窄，且强制绑死旧 `styleId` 枚举**
   - `lib/intent.js` 的 JSON 契约强迫 LLM 在 5 个 `style` 枚举里做选择，且 `clarify` 仅支持 `ratio | style` 两个固定字段。对于真正需要用世界知识帮用户补充关键画面维度（如主体细节、光线氛围、视角景别）或渐进式澄清的场景，现有结构偏死板。
4. **否定表述陷阱与多轮主题漂移**
   - `intent.js` 目前不产出负向提示词建议，用户说“不要文字/不要人”时，LLM 容易直接译成 `no text / no people` 写进正向 Prompt（在扩散模型中往往适得其反）。
   - 多轮对话无条件注入 `previousPrompt` 要求增量合并，当用户换一个全新主题时容易把新主体硬塞进上一轮的背景里。
5. **跨模式状态细节**
   - `ChatPanel.jsx` 空态点击示例按钮时会调用 `patchForm`，跨界改写参数表单的状态。
   - 确认卡默认渲染 `排除项` 文本域（即便当前模型 `cfg === 0`），且缺少抽卡张数控制与“转入参数表单批量调参”的流转入口。

## 三、重构与打磨方向建议

> 以下为推荐的产品与架构方向，重点是**做减法**与**对齐真实能力**，具体实现形态可由 Coding 专员灵活设计。

### 3.1 创作参数面板：轻量、诚实、聚焦高频抽卡

1. **移除 5 个静态「风格预设」方块及黑盒后缀拼接**
   - 让表单回归纯粹，不再在提交时暗箱拼接 `styleSuffix` 或 `style` 负向层（相关前端/契约历史包袱可一并评估简化）。
   - 后期如需提供风格与灵感学习，将由独立迭代的**「灵感图墙 + 模型提炼关键 Prompt」**承接（见第四节）。
2. **按模型能力隐藏「排除项」（选定策略：简洁隐匿）**
   - 当当前模型不支持或默认不使用负向提示词（例如 `cfg <= 0` 或 `negativeHint` 为空且用户未主动抬高 CFG 时），直接在参数表单与对话确认卡中隐藏「排除项」，也不再向请求体预填无效的 `negativeHint`。
   - 仅在模型原生依赖并启用 CFG（如 `SDXL Base`、`RealVisXL`、`Playground v2.5`、`Animagine 3.1` 等）时展示排除项。
3. **理顺「画面设置」并处理与参考图的互斥关系**
   - **有参考图时**：诚实反映后端跟随参考图尺寸的行为——收起或替换「画面设置」，明确告知用户出图尺寸将跟随参考图，不再展示可点却无效的比例按钮。
   - **文生图时**：精简三层冗余。例如保留 5 个画幅比例作为主入口，分辨率档位围绕当前比例做等比缩放（或统一清晰度档位），将「宽 × 高」精确数值输入收进按需展开的「微调」里，从而省掉冗长的文字说明书 `sizeHint`。
4. **高频参数提权与收起态自解释**
   - **「生成张数（1~4）」提权出折叠区**，放在主视线内（如紧凑 4 格分段选择器），匹配「快速换词 + 调比例 + 多张抽卡」核心场景。
   - **「灵感示例」仅在提示词为空时（或按需）出现**，不长期霸占首屏高度；「润色建议」支持快捷收起。
   - **「高级参数」折叠态直接显示当前读数摘要**（如 `4 步 · 随机种子`），Seed 增加快捷重置回随机的操作。
   - **底部生成按钮**附带一行简明规格摘要，让用户在任意滚动位置都能看清即将提交的尺寸、张数与模式；同步更新 `englishPromptHint` 等过时文案，并适当放大 `10.5px` 细小功能字号。

### 3.2 打通「助手」与「表单」：从启发到批量抽卡

- 在对话模式出图或确认后，提供一条顺滑路径把当前整理的 Prompt 与比例带入「参数表单」，方便用户紧接着开启 4 张抽卡或垫图重绘。
- 对话确认卡可考虑精简非必要暴露（如在无需排除项的模型上隐藏 `negative`、让中文摘要更突出），同时补齐张数选择或沿用清晰的默认策略。

### 3.3 AI 助手提示词与模型知识设计原则（软性引导为主）

打磨助手（`intent`、`enhance` 以及 Agent 工具描述）的核心思路，是**把“经验与世界知识”喂给大模型，用软性建议替代硬编码规则**，让大模型自行做出自然判断：

1. **三段式上下文架构（我是谁 → 我有哪些工具与模型 → 如何组织与沟通）**
   - **身份与使命**：明确告诉助手它是面向创作新手的图像生成导演/提示词顾问——用户可能不懂摄影术语、模型架构和英文表达，助手的任务是用最小的沟通成本把用户的想法落地为高出图质量的英文指令。
   - **注入模型库手册与最佳实践（单一来源驱动）**：
     - 从 `models/*.json`（经由 `shared/contract.js`）提取可复用的模型知识摘要，告诉助手当前选用的是哪款模型、它的 `promptStyle`（`concise` / `natural` / `danbooru`）、是否依赖 `CFG > 0` 与负向词、是否支持图生图，以及**整个模型库里还有哪些各具专长的模型**（例如二次元优选、写实人像优选、商业光影、极速草稿）。
     - 这样助手既能写出符合当前模型胃口的 Prompt，也能在用户需求明显更适合另一款模型时，温和地给出切换建议（而不是硬拦或瞎写）。
   - **软性提示词组织与澄清策略**：
     - **避免强硬分支规则**：用引导性、启发式的建议告诉大模型如何工作——例如：鼓励它在保留主体与风格连贯的前提下逐步组织或微调提示词；提醒它感知用户是在“延续上一轮画面修改”还是“开启全新话题”；建议它把主体、场景、光线、视角与材质拆解得具体可感，尽量少堆砌空洞的质量黑话。
     - **正面描述替代否定词**：软性引导大模型根据当前模型是否支持排除项来决定写法——不支持排除项时尽量用正面视觉描述表达“干净/空旷/无遮挡”，避免在正向 Prompt 里出现 `no xxx` 触发反效果。
     - **温和且有价值的澄清**：不再把澄清僵化地限制在两三个固定字段，允许助手在用户描述过于单薄、或存在多条有意思的视觉走向时，给出轻量的引导选项或建议，帮用户毫无压力地把画面想清楚；当意图已经足够明确时则直接组织好参数让用户出图。
2. **`enhance`（润色）与模型配方对齐**
   - 建议让 `lib/enhance.js` 同样以模型资产的真实属性（`promptStyle`、速度档位）为依据，而非维护一份独立且容易过时的硬编码 ID 列表，并引导润色建议避开原文中已经包含的维度内容。

## 四、面向后期迭代的可扩展性预留（本阶段不强求实现）

为避免架构走弯路，在本次梳理模块与接口时，建议对以下两个后续演进方向保持友好（仅作设计参考，不强制本轮编码落地）：

1. **参考图理解 + AI 交互式追问（超越“盲目直接重绘”）**
   - **未来场景**：用户上传或选择一张参考图后，先经由具备视觉理解能力的大模型识别图片内容，由 AI 猜测并询问用户想做什么（例如：“我看到图里有一位穿风衣的人物在雨夜街道，你是想**保持构图换个白天场景**、**保留人物换二次元画风**，还是**微调光影细节**？”），确认意图后再组织 Prompt 交给图生图管线。
   - **接口预留建议**：`lib/llm.js` 的消息构造可保留扩展到多模态内容块（`text` + `image`）的空间，对话态数据不必将消息严格锁死为纯文本。
2. **灵感图墙 + 模型提炼关键 Prompt**
   - **未来场景**：用社区/本地作品图墙替代静态风格按钮来提供灵感；结合大模型或轻量模型对图墙作品进行分析，自动高亮/拆解“是哪几个关键 Prompt 词决定了画面的核心质感或构图”，让用户在看图的过程中自然学会写词。

## 五、给 Coding 专员的落地提示

- **兼容性与测试**：项目具备较完备的契约校验（`npm run test:contract`）与离线逻辑/渲染测试（`npm run test:client`、`npm run test:host`），若调整 `STYLE_IDS`、`intent` 返回结构或表单字段，请同步审视 `shared/contract.js`、`src/dict/zh.js` & `en.js` 以及对应的测试用例与 `docs/SPEC.md` / `docs/DESIGN.md`。
- **分步建议（仅供参考，可自行调整）**：可考虑将「助手层梳理与提示词打磨」与「参数面板减法重构」拆开推进，每一步保持可独立验证与回归。
